Dwarpal — Zero to Hero

A book that takes you from "I have never written a line of code" to "I understand — line by line — how a real AI system that protects children online is designed, built, tested, deployed and defended."

Explain like I'm six

Imagine a door to a room that only grown-ups are allowed to enter. Next to the door stands a guard. In old Indian temples the guard who stands at the door is called a dwarpal (द्वारपाल — dwar means "door", pal means "keeper").

Our project builds a computer guard for doors on the internet. When someone tries to open a website that is only for grown-ups, the computer guard takes a quick look through the camera, makes a careful guess about whether the person is a grown-up, and then — this is the important part — forgets the face immediately. It only remembers "this person was allowed in" or "this person was not allowed in".

This book teaches you everything needed to build that guard — starting from "what is a computer?"

What this book is

This is a single, self-contained book about one project: an AI-based age estimation system for protecting minors from accessing age-restricted online content, code-named Dwarpal.

It is written for a reader who knows nothing about computers, programming, websites, servers or artificial intelligence. Every idea is introduced before it is used. Every word that might be new is explained the first time it appears, and again in the Glossary. Hover over words with a dotted underline (like API or HTTP) to see a short definition.

The book does three jobs at once:

  1. It teaches the foundations — computers, the internet, websites, databases, servers, AI — from scratch.
  2. It records the thinking — why this project is built the way it is, which alternatives were considered, and why they were rejected. In engineering, the why matters as much as the what.
  3. It explains every line of code — every single line of every file in the project, in plain language, right next to the code itself.

The 60-second version of the project

  1. A website that sells something grown-ups-only (or shows grown-ups-only content) needs to know whether a visitor is old enough. Laws in the UK, the EU, the US, Australia and India now require many websites to check this properly.
  2. Asking "Are you 18? Yes/No" doesn't work — children just click "Yes".
  3. Our system lets the website send the visitor to a verification page. The visitor looks at their camera for about three seconds and follows two or three random instructions ("turn your head left", "look up") while the screen glows softly in random colours.
  4. On our server, an AI model estimates the visitor's age as a range with a confidence level, and checks that a real, live person was in front of the camera (not a photo, a video, or a video-game character).
  5. A decision engine compares the estimate against the website's rule (for example "18+") using a carefully calculated safety margin. The answer is pass, fail, or "not sure — please use another method".
  6. The website receives a digitally signed answer — like a letter with a wax seal that cannot be forged — saying only "this person is over 18: yes". It never receives the face, the estimated age, or the person's identity.
  7. The face images are deleted from memory within about a second. They are never saved anywhere.

Part 0 — Absolute basics

This part assumes you know nothing. If you already know what a server, an API and a database are, skim it. Every later part builds on it.

0.1 What is a computer?

A computer is a machine that does exactly three things, over and over, billions of times per second:

  1. Takes in information (input) — key presses, mouse clicks, a camera picture, a message from the internet.
  2. Works on that information (processing) — adds numbers, compares them, moves them around.
  3. Gives out a result (output) — pixels on the screen, sound, a message sent back over the internet.

Explain like I'm six

A computer is like a very fast, very obedient cook who can't think for themselves. You give the cook ingredients (input), a recipe (the program), and the cook produces a dish (output). The cook will follow the recipe exactly — even if the recipe says "add 100 spoons of salt". The cook never asks "are you sure?".

The important parts inside a computer:

Part What it does Everyday comparison
CPU (Central Processing Unit) Follows instructions, one tiny step at a time, extremely fast The cook's brain and hands
GPU (Graphics Processing Unit) Does thousands of simple maths operations at the same time. Built for drawing graphics; perfect for AI A kitchen with 5,000 helpers who can each only chop, but all chop at once
RAM (memory) Holds what the computer is working on right now. Fast, but forgets everything when power is off The kitchen counter — you put things there while cooking
Storage (SSD / hard disk) Keeps files permanently, even when power is off The cupboard

The computer this project is being built on has an Intel Core i9-14900HX CPU, an NVIDIA GeForce RTX 4070 Laptop GPU with 8 GB of its own memory, and 32 GB of RAM. That GPU matters: it is what will make training our AI model (Part 2) take hours instead of weeks.

Key idea — everything is numbers

Inside a computer, everything — text, photos, music, videos, programs — is stored as numbers. The smallest unit is a bit: a single 0 or 1 (think of a light switch, off or on). Eight bits make a byte, which can hold a number from 0 to 255.

  • 1 kilobyte (KB) ≈ 1,000 bytes — about a paragraph of text
  • 1 megabyte (MB) ≈ 1,000,000 bytes — about one phone photo
  • 1 gigabyte (GB) ≈ 1,000,000,000 bytes — about a film

A photo is stored as a grid of tiny dots called pixels, and each pixel is three numbers: how much Red, Green and Blue light it has (each 0–255). A 640 × 480 camera picture is therefore 640 × 480 × 3 = 921,600 numbers. When our AI "looks at a face", it is really doing arithmetic on numbers like these. Part 2 shows exactly how.

0.2 Files, folders and paths

A file is a named bundle of bytes kept in storage: a photo, a document, a program. A folder (also called a directory) is a container for files and other folders, so they form a tree.

The path of a file is its full address in that tree. On Windows a path looks like this:

C:\Users\anubh\Projects\AI_based_minor_protection\docs\zero_to_hero\build.py

Read it left to right: drive C:, then folder Users, inside it folder anubh, … and finally the file build.py. The part after the last dot, .py, is the extension. It hints at what kind of file it is (.py = Python program, .html = web page, .md = Markdown text, .json = data, .jpg = photo).

Careful — two kinds of slashes

Windows separates folders with a backslash \. Linux and macOS — and web addresses — use a forward slash /. Our code must run on both (development on Windows, servers on Linux), so it uses tools that handle either. In this book we usually write paths with /, like docs/zero_to_hero/build.py. That kind of path, measured from the project's main folder, is called a relative path.

Text files and encodings

Some files contain text (letters you can read); others contain binary data (photos, programs). But text is numbers too: each letter needs a number. The agreement that says "the number 65 means A" is called a character encoding.

The modern encoding is UTF-8. It can store every character in every language — English, हिन्दी, emoji 🧒 — and it is what every file in this project uses.

Real world — what goes wrong when encodings disagree

If a program writes a file in UTF-8 but another program reads it assuming an older encoding (such as Windows-1252), characters turn into garbage called mojibake. A long dash "—" becomes "â€”". This exact bug appears in the HTML documentation of a previous project by the same team. That is why the builder of this book reads and writes every file as UTF-8 explicitly — you will see the exact line in Part X.

0.3 What is a program?

A program is a file (or many files) of instructions for the computer. The instructions are written by people, in a programming language, as plain text. That text is called source code, or just code.

Explain like I'm six

A program is a recipe. A recipe for tea might say:

  1. Fill the kettle with water.
  2. Switch it on.
  3. If you want it sweet, add sugar.
  4. Repeat stirring 5 times.

Programs have exactly these ingredients: steps in order, decisions ("if …"), and repetition ("repeat …"). Everything else is detail.

Programs are precise. A human understands "add some sugar"; a computer needs "add 2 spoons". Most of programming is turning a fuzzy human wish into precise steps — and most bugs come from a step that wasn't quite what the programmer meant.

0.4 Programming languages

Computers really only understand machine code: long lists of numbers that mean things like "add these two" or "jump to step 7". Humans can't comfortably write that, so we write in programming languages that read almost like English. Other programs then translate them for the computer.

Language Used in this project for What it looks like
Python The servers (backend), the AI, the tools (including the one that builds this book) if age >= 18: print("welcome")
TypeScript The websites people see (frontend). It is JavaScript with extra safety checks called types if (age >= 18) { show("welcome") }
JavaScript What web browsers actually run. TypeScript is converted into it same as above, minus the types
HTML Not a programming language — a markup language that describes what's on a web page <h1>Welcome</h1>
CSS A style language: colours, sizes, layouts h1 { color: blue; }
SQL The language for asking a database questions SELECT * FROM sessions WHERE outcome = 'pass'

There are two broad ways a language gets run:

  • Interpreted (Python, JavaScript): another program — the interpreter — reads your code and does what it says, line by line, while it runs.
  • Compiled (C, Rust, Go): a compiler translates the whole program into machine code first, producing a file that runs directly.

Why Python for the backend and the AI?

Nearly every modern AI tool (PyTorch, ONNX Runtime, OpenCV, MediaPipe) is built for Python first. Using Python for both the AI and the servers means one language for the whole back half of the system — and one language for you to learn. The speed cost of an interpreted language barely matters here, because the slow part (the AI maths) runs inside highly optimised libraries written in faster languages.

0.5 The terminal

Before mouse-and-window interfaces, people used computers by typing commands. That way of working still exists and programmers use it constantly. The window you type commands into is called a terminal (on Windows: PowerShell or Command Prompt). The program that reads your commands is called a shell.

Try it yourself

Open PowerShell (press the Windows key, type PowerShell, press Enter) and type:

python --version

and press Enter. The computer answers with something like Python 3.14.6. You just asked a program a question and got an answer — that is what every command does.

Throughout this book, commands you can type are shown in boxes like this:

python build.py

0.6 How computers talk: networks and the internet

A network is computers connected so they can send each other messages. The internet is the network of all networks — billions of devices.

Messages travel in small chunks called packets. To deliver a packet, the network needs an address:

  • An IP address is a computer's address on a network, like a house address. It looks like 142.250.183.14 (IPv4) or a longer form with colons (IPv6).
  • A port is a numbered door on that computer (0–65535). One computer can run many programs that talk to the network; each listens behind its own door. Web traffic usually uses door 443 (secure) or 80 (old, insecure).

Explain like I'm six

The IP address gets the letter to the right building. The port number gets it to the right flat inside the building. Every program that wants to receive letters must sit behind a flat door with a number on it.

  • localhost (or 127.0.0.1) is a special address that always means "this same computer". When we run the project on our own laptop, we visit addresses like http://localhost:3000.
  • DNS (Domain Name System) is the internet's phone book. Humans remember names like google.com; DNS translates them into IP addresses. When we put Dwarpal on the internet, we'll buy a name and add a DNS record pointing it at our server's IP address.

0.7 Clients and servers

Most internet programs come in pairs:

  • A client asks for something. Your web browser is a client.
  • A server answers. It is a program that starts up and then waits — forever — for clients to ask it things. Waiting for messages on a port is called listening.

Explain like I'm six — the restaurant

You sit at a table and order (you are the client). The waiter takes your order to the kitchen (the server — it waits all day for orders). The kitchen prepares the dish and sends it back. You never go into the kitchen, and the kitchen never comes to your house. The menu tells you what you're allowed to order.

The word "server" means two things — the program that answers and the computer it runs on. When people say "the website is on a server", they mean a computer, usually in a data centre, running server programs 24 hours a day.

Dwarpal has several servers. Each is a program with its own job, and each listens on its own port:

Server Its job Language
Web app Sends the pages you see in your browser TypeScript (Next.js)
API The "brain office": sessions, rules, decisions, signed answers Python (FastAPI)
Inference service The "AI room": looks at the frames and does the maths Python + ONNX Runtime
Database Remembers things long-term PostgreSQL
Valkey Remembers things short-term, very fast Valkey

0.8 HTTP — the language of the web

When a client and a server talk, they need an agreed protocol: rules for how messages are formatted. The web's protocol is HTTP (HyperText Transfer Protocol).

Every HTTP conversation is one request followed by one response.

A request has:

  • a method — what kind of action is wanted;
  • a path — which thing it's about;
  • headers — extra labels, like the envelope of a letter;
  • (sometimes) a body — the contents, like the letter inside.
POST /v1/verification-sessions HTTP/1.1
Host: api.dwarpal.example
Authorization: Bearer dk_test_EXAMPLEKEY000000000000
Content-Type: application/json

{"policy": "uk_osa_18_standard", "return_url": "https://shop.example/age-ok"}

The common methods:

Method Means Example in Dwarpal
GET "Give me this" (never changes anything) Get the result of a verification session
POST "Create something / do something" Create a new verification session
PUT / PATCH "Replace / update this" Change a policy
DELETE "Remove this" Revoke an API key

A response has a status code (a three-digit number that summarises what happened), headers, and usually a body:

HTTP/1.1 201 Created
Content-Type: application/json

{"id": "vs_01JA8...", "url": "https://verify.dwarpal.example/s/vs_01JA8...", "status": "pending"}
Code Name Means
200 OK Here's what you asked for
201 Created I made the thing you asked me to make
204 No Content Done; nothing to send back
301 / 302 Moved Look over there instead
400 Bad Request Your request doesn't make sense
401 Unauthorized I don't know who you are (missing or wrong key)
403 Forbidden I know who you are, but you're not allowed
404 Not Found That doesn't exist
409 Conflict That clashes with something that already happened
422 Unprocessable I understood the format, but the values are invalid
429 Too Many Requests Slow down — you're over your limit
500 Internal Server Error Something broke on my side
503 Service Unavailable I can't answer right now, try later

Key idea

The first digit tells you who is responsible: 2xx = success, 3xx = go elsewhere, 4xx = the client made a mistake, 5xx = the server made a mistake. Dwarpal follows these rules carefully, because the websites that use it will write code that reacts to these numbers.

0.9 HTTPS — the padlock

Plain HTTP travels like a postcard: anyone the message passes through can read it. HTTPS is HTTP inside a sealed, tamper-proof envelope. The sealing technology is called TLS (Transport Layer Security). The padlock icon in your browser means "this conversation is sealed".

The server proves its identity with a certificate: a digital document, signed by a trusted organisation, saying "this server really is dwarpal.example".

Key idea — why HTTPS isn't optional for us

Browsers refuse to give a web page access to your camera unless the page is served over HTTPS (or from localhost during development). This is a deliberate browser security rule. Our whole system depends on the camera, so HTTPS is built in from day one. We'll use a program called Caddy that gets and renews certificates automatically.

When you open a website, your browser asks a server for files and turns them into the page you see. There are three kinds:

  • CSS is the puppet's clothes and paint: colours, sizes, where things sit.

0.11 APIs and JSON

An API (Application Programming Interface) is a menu of requests that one program offers to other programs. A website shows buttons to humans. An API offers endpoints — specific paths and methods — to other programs. For example, POST /v1/verification-sessions is one endpoint on Dwarpal's API.

When programs exchange data, they need a shared format. The most common is JSON (JavaScript Object Notation). It is plain text with just six kinds of value:

Kind Looks like Means
String "hello" Text, always in double quotes
Number 42, 0.97 A number
Boolean true / false Yes or no
Null null "Nothing here"
Array [1, 2, 3] An ordered list
Object {"age_over": 18} Labelled values ("key": value) 
{
  "id": "vs_01JA8XQ2",
  "outcome": "pass",
  "age_over": 18,
  "methods": ["face_estimation", "liveness_active"]
}

That is everything — all JSON is these six kinds nested inside each other.

0.12 Databases

Programs forget everything when they stop, like the kitchen counter being wiped clean every night. A database is a program that remembers, safely and permanently, and can quickly answer questions about what it remembers.

The most common kind is a relational database. It stores data in tables, a bit like spreadsheets:

id policy outcome created_at
vs_01JA8XQ2 uk_osa_18_standard pass 2026-10-15 10:02
vs_01JA8XR7 uk_osa_18_standard step_up 2026-10-15 10:03

Each row is one thing (here, one verification session). Each column is one property of it. You talk to it in SQL:

SELECT outcome, COUNT(*) FROM verification_sessions GROUP BY outcome;

That asks: "for each outcome, how many sessions had it?"

Why a real database instead of saving files?

Two people can't safely write to the same file at the same moment. A database handles thousands of simultaneous readers and writers without corrupting anything. It guarantees that a group of changes either all happen or none happen — this is called a transaction. It also enforces rules ("every session must belong to a project"). Dwarpal uses PostgreSQL, one of the most trusted databases in the world.

0.13 Where websites live: hosting, the cloud and domains

To be reachable by everyone, our servers must run on a computer that is always on and connected to the internet. Your laptop sleeps and moves around, so instead we rent a computer in a data centre.

  • Hosting = renting space and computing power to run your website.
  • The cloud = companies (Amazon Web Services, Google Cloud, Microsoft Azure, Hetzner, Oracle Cloud, …) that rent out computers by the hour or month.
  • A VM (virtual machine) or VPS (virtual private server) = a slice of a big computer that behaves like your own private computer.
  • Deploying = copying your program onto that rented computer and starting it.
  • A domain = the human-friendly name (like dwarpal.example) that you rent from a registrar, then point at your server with DNS.

Explain like I'm six

Your laptop is your home kitchen. Hosting is renting a stall in a big food market that never closes. The domain name is the sign above your stall, so people can find it. Deploying is carrying your recipes and ingredients to the stall and starting to cook there.

0.14 Containers and Docker

Software that works perfectly on your laptop often breaks on a server: a different operating system, a missing library, a different version of Python. Docker solves this by packing a program together with everything it needs into one sealed box.

Word Meaning Lunchbox comparison
Image The sealed, read-only package: the operating system bits, the language version, the libraries, your code A packed lunchbox recipe — the same every time
Container A running copy of an image An actual lunchbox, opened and being eaten
Volume A folder that survives when the container is thrown away A thermos you keep and refill
Docker Compose A file that describes several containers that work together, and starts them all with one command A picnic plan: "three lunchboxes, two thermoses, start them together"

Dwarpal will start completely — web app, API, AI service, database, everything — with one command:

docker compose up

0.15 Git — a time machine for code

Git is a tool that records the history of a project.

  • Every time you reach a good point, you make a commit: a snapshot of all files plus a message saying what changed and why.
  • You can go back to any earlier snapshot, compare two snapshots, or work on an experiment in a separate branch without disturbing the main version.
  • GitHub is a website that stores Git projects online, so teams can share them and computers can automatically test every change.

Explain like I'm six

Git is a "save game" button for code. Every save has a name and a note. If you break something, you load the last good save.

0.16 Open source and licences — why "free to download" isn't "free to use"

A huge amount of software (and many AI models and datasets) is open source: the code is published for anyone to read. But publishing is not the same as permission. Every project comes with a licence — the legal rules for what you may do with it.

Real world — licences shaped this project's design

  • The popular YOLOv8 face detector is AGPL, so we chose YuNet (MIT licence) instead.
  • Many well-known face datasets used to train age models (IMDB-WIKI, UTKFace, …) are research-only. Our AI model can be trained on them for this project, but a company selling Dwarpal would have to retrain on properly licensed data.

That is why the system treats the AI model as a replaceable part with a version number, not as something welded in. Part 3 explains this decision.

0.17 Libraries, packages and versions

Nobody writes everything from scratch. A library (or package) is code someone else wrote and shared, so you can use it. Examples: a library that reads photos, a library that does the AI maths, a library that turns Markdown into HTML.

  • A package manager downloads libraries for you: pip or uv for Python, npm or pnpm for JavaScript.
  • Libraries have version numbers such as 3.11.1. These are usually major.minor.patch: a bigger last number means a small bug fix, a bigger middle number means new features, and a bigger first number may mean breaking changes.
  • Pinning means writing down the exact version you tested with (like markdown==3.11.1). Then the project builds the same way next month, on another computer, or on a server.
  • A lockfile (uv.lock, pnpm-lock.yaml) is an automatically generated list of the exact versions of every library, including the libraries your libraries use.

Careful

"It worked yesterday" bugs very often come from a library quietly updating itself. Pinning versions prevents that. Every library in Dwarpal is pinned.

0.18 Putting it all together — the journey of one age check

Here is everything from Part 0 in one story. Later parts explain each step in depth.

  1. Asha, 26, visits a (fictional) online shop that sells wine. Her browser (a client) asks the shop's server for a page using HTTPS.
  2. The shop must check her age. Its server sends a POST request to Dwarpal's API, authenticated with the shop's secret API key. Dwarpal's API saves a new session in the database and replies with JSON containing a link.
  3. Asha's browser opens Dwarpal's verification page (HTML, CSS, JavaScript). With her permission — only possible because the page uses HTTPS — it turns on the camera.
  4. JavaScript running in her browser helps her line up her face. Then it sends a few camera frames (photos, which are just numbers) to the API.
  5. The API passes them to the inference service. There, the AI model — running on the CPU — turns the numbers into an age estimate and a liveness check. The frames are then forgotten.
  6. The API's decision engine says pass. It creates a digitally signed answer and records "pass" (never the face) in the database.
  7. Asha's browser goes back to the shop. The shop's server checks the signature and lets her buy the wine.

All of this runs inside Docker containers on a rented VM reachable at a domain name. The code is tracked with Git, built from pinned libraries with suitable licences.

Part 1 — The problem

1.1 A story

Riya is 14. She has a phone, like most of her friends. One evening a link in a group chat leads to a website showing violent videos that are made for adults. The site has a little box: "Are you 18 or older? [Yes] [No]". Riya taps Yes. Nothing stops her.

Nobody did anything illegal by building that box. Until recently, in most countries, that box was considered "enough". That has now changed. Governments around the world have decided that websites with adult content must actually check age, not just ask.

This project is about building that check properly — so that it really works, is fair to everyone, and does not turn into a surveillance machine.

1.2 What is "age-restricted content"?

Anything the law, or a website's own rules, says should only be available above a certain age:

Kind of content or service Typical minimum age (varies by country)
Pornography and sexually explicit material 18
Online gambling and betting 18 (21 in some US states)
Alcohol, tobacco and vape sales 18 (21 in the US)
Graphic violence, self-harm and suicide content 18 (or "not for children")
Social media accounts 13 in many places; 16 in Australia since December 2025
Some games and in-app purchases 12, 16 or 18 depending on rating
Processing a child's personal data at all (India) Under 18 needs a parent's verifiable consent

Key idea

The age limit is not always 18. That is why Dwarpal treats the age limit as a setting each website chooses (13, 16, 18, 21…), never as a number fixed inside the code.

1.3 Why "Are you 18? Yes / No" doesn't work

A self-declaration box checks nothing — it trusts the person it is supposed to check. Typing a date of birth is the same thing in a different costume: children simply type an earlier year. Regulators now say this plainly. The UK regulator Ofcom states that self-declaration does not count as effective age checking.

So we need something that does not depend on the person telling the truth.

1.4 What the law now says — a world tour

Explain like I'm six

Different countries have made slightly different rules, but they all say roughly the same thing to websites: "If you show grown-up stuff, you must really check who is a grown-up — and you must do it fairly, safely, and without being nosy."

Real world

In its first six months (July–December 2025), the UK system processed around 69 million age checks across 32 large services. The two most common methods were face-based age estimation and photo-ID matching. This is not a classroom problem — it is happening at enormous scale right now.

1.5 Three ways to know someone's age

Explain like I'm six — three ways a shopkeeper can know your age

  1. Verify: you show your birth certificate or ID card. The shopkeeper reads your birth date. (Very sure — but you have shown your name, address and photo too.)
  2. Estimate: the shopkeeper just looks at you and guesses. (Quick and private — but sometimes wrong.)
  3. Infer: the shopkeeper notices clues — you drove here yourself, you are paying with a credit card. (Indirect.)
Method Official name Strength Weakness
ID card, passport, bank, digital ID app Age verification Exact date of birth Reveals identity; not everyone has ID; documents can be faked or borrowed
Looking at the face (or voice, or hand) Age estimation Fast, no documents, can reveal nothing but "over/under" It's a guess; it can be wrong, especially close to the limit
Other facts (credit card, account history, email history) Age inference Invisible to the user Indirect; needs extra data about the person

All three together are called age assurance. Dwarpal uses estimation first (fast and private). It falls back to verification only when the estimate is too close to call.

1.6 How can a computer guess age from a face?

Faces change with age in ways we all recognise: proportions change as children grow, skin texture changes, bone structure matures, and later come wrinkles and grey hair. An AI model learns these patterns by looking at hundreds of thousands of face photos whose real ages are known — the same way you learn to guess ages by meeting many people. Part 2 explains exactly how that learning works.

Honest limitation

Faces don't come with birth certificates. Some 16-year-olds look 20; some 20-year-olds look 16. Make-up, beards, lighting, camera quality, health and family genes all change how old someone looks. Even humans are often wrong by several years. No AI can remove this uncertainty completely. A good system doesn't pretend otherwise — it measures its uncertainty and acts carefully when it is unsure.

1.7 The two kinds of mistakes

Whenever a guard decides "allowed" or "not allowed", there are two ways to be wrong:

Guard says "grown-up, come in" Guard says "not sure / no"
Really a child ❌ Dangerous mistake — a child gets in ✅ correct
Really a grown-up ✅ correct ⚠️ Annoying mistake — an adult is held up

Explain like I'm six — the swimming pool

A swimming pool has a deep end only for strong swimmers. The lifeguard can make two mistakes: letting in a child who can't swim (dangerous!), or stopping a good swimmer (annoying, but nobody gets hurt). A sensible lifeguard is stricter about the dangerous mistake, and gives the stopped swimmer a fair way to prove themselves — "swim one length for me".

These two mistakes are not equally bad. Our whole design is built around that fact:

  • We measure the dangerous mistake carefully, separately for every age (13, 14, 15, 16, 17). We call it the false-adult rate.
  • We set a strict limit on it — for example "at most 2 in every 100 children near the age limit may get through" — and calculate the guard's settings to respect that limit. (The exact method is in Part 3.)
  • We give adults who were held up a fair second route (another method), instead of just saying "no".

Real world — why this matters so much

A February 2026 research benchmark tested 34 freely available AI age-guessing models. Most of the specialised ones called 39–100 % of children "adults" when the limit was 18. Even huge general-purpose AI models made that mistake 16–29 % of the time. The best commercial systems, measured by the US standards body NIST, let through roughly 5 % of minors when they use a safety margin. So "just download a model" is not safe. The gap between those numbers is what this project's engineering is for.

1.8 The safety margin: "Challenge 25"

Shops in the UK selling alcohol follow a rule called Challenge 25: the law says 18, but staff ask for ID from anyone who looks under 25. The extra seven years are a buffer. A 17-year-old might be mistaken for 19, but very rarely for 25.

Age-estimation systems use exactly the same trick, called a challenge age or buffer. The US National Institute of Standards and Technology (NIST), which tests these systems, measures them this way — for example "accept only if the estimate is 25 or more, for a legal age of 18".

Explain like I'm six — the fairground ride

A ride says "you must be 120 cm tall". The measuring stick is wobbly. So the operator says: if the stick shows 130 cm or more, go straight in. If it shows less, let's measure you properly with the good tape. The extra 10 cm protects against the wobbly stick.

1.9 When the guard isn't sure: "step-up"

What happens to a 20-year-old who looks 19? With a buffer of 25, the guess "19" is not enough to let them in. But we also can't be sure they are a child. So the answer is neither "yes" nor "no", but:

"I'm not sure. Please use another method."

This is called step-up: moving to a stronger check, such as an ID document or a digital ID app. Australia's government trial called this a waterfall: try the quick, private method first; flow down to a stronger method only when needed.

Dwarpal therefore has three main answers, not two: pass, fail, and step-up. (Plus retry when the picture was too dark or blurry, and reject when it looks like someone is cheating.)

1.10 Cheaters: how people try to fool the guard

If there's a gate, someone will try to sneak past. The cheating tricks have names:

Trick Example Official name
Hold up a photo of an adult Printed photo, or a photo on another phone Presentation attack (print / screen)
Play a video of an adult A recorded video on a tablet Replay attack
Use a fake face A mask; heavy make-up; a fake beard Presentation attack (mask / disguise)
Use a computer-generated face A video-game character, a 3D avatar, a deepfake Presentation / injection attack
Skip the camera completely Software that pretends to be a camera and feeds in a fake video Injection attack
Ask a grown-up to do it An older sibling or parent looks at the camera Proxy
Try again and again Different lights and angles until it says yes Trial-and-error

Real world — the video-game trick, July 2025

Days after the UK's new rules started in July 2025, people discovered that Discord's face-based age check could be passed with a video-game character. The game Death Stranding has a "photo mode" that lets you move a very realistic character's face. Its controls could even open and close the mouth, which was exactly what Discord's "liveness" step asked for. Reports say characters from other games worked too.

Lesson for us: a simple, predictable "liveness" test (blink, open your mouth) is not enough any more. Part 3 describes our layered defence: random head-movement instructions that can't be prepared in advance, and a screen-light check — the screen glows in a secret random sequence of colours, and a real face reflects that light in a way a pre-made video or a game character cannot know ahead of time.

Honest limitation

No age check can stop a willing adult from doing the check for a child (a "proxy"). Regulators accept this. What we can do is make sure a real, live person was present at the moment of the check, keep the result short-lived, and tie it to the specific website visit.

1.11 Privacy: "look, decide, forget"

Faces are biometric data — information about your body. If a company kept millions of children's face photos, a single data leak would be a disaster.

Key idea — Dwarpal's privacy promise

  1. Look: the camera frames are used only to make the decision.
  2. Decide: the system produces "pass", "fail" or "step-up".
  3. Forget: the frames are erased from memory within about a second. They are never written to a disk, a log file or a database. There is literally no place in the system where a face could be saved.
  4. Say as little as possible: the website learns only "over 18: yes" (or no). Not the guessed age. Not a name. Not anything that could link the same person across different websites.

There is a saying in security: you can't leak what you never kept.

1.12 Fairness: the same rules for every face

AI models learn from examples. If the examples contain mostly one kind of face — say, light-skinned adult film stars — the model will be worse at guessing other faces. Research, including NIST's testing and Australia's trial, has found exactly this: some systems make more mistakes for some skin tones, for women, or for certain age groups.

An unfair age check is dangerous in both directions:

  • it can let more children through for some groups (unsafe);
  • it can block more adults from some groups (discriminatory).

Dwarpal will measure its mistakes separately for different groups, using research datasets that carry those labels. It will refuse to release a model whose groups differ too much. And it will never try to guess a person's skin colour or sex during a real check — those labels are only used offline, to test the model.

1.13 What our system must do — in plain words

  1. Let any website ask: "Is this live person over N years old?"
  2. Give the person a quick (under 15 seconds), clear, kind experience on any phone or computer.
  3. Make a careful guess, with a measured level of confidence, and be extra careful near the age limit.
  4. Detect cheating: photos, videos, masks, computer-generated faces, fake cameras, repeated tries.
  5. Answer pass, fail, step-up, retry or reject — and when something goes wrong inside the system, never answer "pass" by accident. This is called failing closed.
  6. Send the website a digitally signed answer that cannot be forged, containing as little information as possible.
  7. Never keep faces.
  8. Measure and publish how often it makes each kind of mistake, for each age and each group.
  9. Give website owners a dashboard: their settings, their keys, their statistics — never anyone's face.
  10. Be easy for websites to plug in, and easy for us to run, update and repair.

1.14 What our system will never do

  • Recognise who you are. It answers "how old do you look?", never "who are you?".
  • Store your face, even "to improve the AI".
  • Guess your race or sex during a check.
  • Promise to be perfect. It states its error rates openly instead.

1.15 How we'll know we succeeded

  • The whole system starts on a laptop with one command, and runs on the internet over HTTPS.
  • A demo shop accepts or refuses visitors using the real system.
  • We publish, for the AI model: how often children near each age limit would get through, how often adults are held up, and how this differs between groups.
  • Our own cheating tests (photos, screen videos, game characters, replayed data) are stopped.
  • Security scans are clean, and the system stays fast under load.
  • This book explains 100 % of the code, and the ledger at the end proves it.

3.2 Stage 1 in plain words — what we found

The full analysis is in docs/design/01_problem_analysis.md. Its main conclusions are below.

  1. This is a trust problem with an AI inside, not an AI problem. A website must be able to trust a yes/no answer about age. The answer must be safe from forging and fair to everyone, and the website must never learn who the person is. A model on its own does none of that.

  5. The hard parts are:
    • data — few photos of teenagers exist, and most face datasets are "research only";

    • privacy — faces are biometric data;
    • fairness — errors are uneven across groups;
    • friction — every extra second loses people.

Choice 1 — What shape is the product?

Choice 2 — What tells us the age?

We compared face video, a single face photo, voice, hand photos, writing style, ID documents, digital-ID apps, and credit or email history.

Choice 4 — The AI model itself

We compared five approaches:

Approach What it is Verdict
Download a ready-made free model Quick ❌ Unsafe — most call many minors "adults"
Pay a cloud company to guess ages Quick ❌ Faces leave our control; costs per check
Ask a giant general AI (like Gemini) Surprisingly good on average ❌ Faces leave our control; slow; still calls 16–29 % of minors "adults"

Our model will not answer "this person is 22". It answers with a probability for every age from 0 to 100: "probably 22; quite possibly 19–25; very unlikely to be under 17". From that one answer we can read off the chance that the person is over 13, 16, 18 or 21 — whatever the website needs.

The guard's line — calculated, not guessed

This is the most important idea in the design.

Explain like I'm six — the jar of photos

Imagine a jar holding 600 photos of real 17-year-olds, ones the model has never seen. We show every photo to our guard and count how many it would wrongly let in.

Say 6 of the 600 get in. That's 1 %. But 600 is not infinity — maybe we got lucky with this jar. So we ask a careful maths question: "Given that 6 of 600 got in, what is the worst the real rate could plausibly be?" The answer, with 95 % confidence, is 1.96 %.

Our rule says "at most 2 %". 1.96 % is under 2 %, so this setting is allowed. If 7 of 600 had got in, the worst plausible rate would be 2.18 % — too high. Then we make the guard stricter and test again.

With a smaller jar of only 300 photos, just 1 child getting through is the most we could accept. A smaller jar means more doubt, so the guard has to be stricter. Less evidence forces more caution.

The maths in the box is called a Clopper–Pearson confidence bound. Part 2 explains it properly. In engineering terms:

  1. The website's policy states a risk budget — for example, "at most 2 % of 13–17-year-olds may pass, with 95 % confidence".
  2. We test the model on held-out photos of children of each age (13, 14, 15, 16, 17), and of each group of people for which the test data has labels.
  3. We choose the least strict line that keeps the worst plausible pass rate under the budget for every one of those ages and groups.
  4. A second, lower line marks when we are confident someone is under the limit. Everyone between the two lines gets step-up, not a rejection.

Honest limitation

The guarantee holds for photos like the ones we tested with — mostly photos from public research collections. Real webcam pictures can be darker, blurrier and taken at stranger angles. We protect against that difference in four ways:

  • refusing poor-quality frames;
  • training on deliberately "webcam-ified" photos;
  • adding an extra safety margin;
  • watching the live pass rates for unexpected changes.

But we say it out loud: the guarantee is about the test photos, not a promise about every webcam on Earth.

Choice 5 — Finding the face

To estimate age we first have to find the face in the picture, and the eyes and nose inside the face. We compared several face finders and picked:

  • YuNet on the server — small, fast, and MIT-licensed.
  • MediaPipe Face Landmarker in the browser — it finds 478 points on the face in real time, which is how we can coach the user and track their head movements.

We rejected two popular alternatives because of their licences: one forbids commercial use, the other (AGPL) would force us to publish all our code under its terms. See §0.16.

Choice 6 — Catching cheaters: an onion of defences

No single test catches every trick, so we stack independent layers. A cheater has to beat all of them at once.

Layer Catches
1. Picture quality check — sharp? bright enough? exactly one face? big enough? Garbage pictures, and people trying from far away
2. "Is it a real face?" model (passive anti-spoofing) Printed photos and phone screens
3. Random instructions — e.g. "turn left, then look up" — different every time Photos and pre-recorded videos
4. Screen-light check — the screen glows softly in a random colour sequence, and a real face reflects it Videos played to the camera, fake cameras, game characters (none can know the colours in advance)
5. Fake-camera clues — suspicious camera names, robot-like timing Software pretending to be a camera
6. (Later) a detector for computer-generated faces Game characters and 3D avatars

Careful — safety for people with epilepsy

Rapidly flashing colours can trigger seizures in people with photosensitive epilepsy. The international accessibility rules (WCAG) require fewer than three flashes per second. Our screen-light check uses slow, gentle colour changes that stay well within those rules, and anyone can choose another method instead.

Choice 8 — The stronger second method (step-up)

When the face check is unsure, the visitor needs another way to prove their age. All the options plug into the same "socket", so more can be added later:

  • ID document scan — read the machine-readable lines at the bottom of a passport or ID card. Those lines include check digits, a little arithmetic trick that catches typing errors. A web browser can't read the passport's chip, so a well-made fake could fool this. We label it honestly as a basic check.
  • Aadhaar Secure QR (India) — the QR code on Aadhaar is digitally signed by the government authority UIDAI, so the date of birth can't be forged. But Aadhaar data is sensitive and heavily regulated.
  • Digital ID apps — such as the EU's age-verification app and digital wallets. Excellent and private, but still rolling out in 2026.

Which one we build first is one of the owner's decisions (§3.6).

Choice 9 — Sending the answer: the wax seal

Explain like I'm six — the wax seal

Long ago, kings sealed letters with wax pressed by a special ring. Anyone could read the letter, but nobody could forge the seal without the ring. If the letter was changed, the seal broke.

Our answer to the website is a letter like that, called a signed token. Our server has the secret "ring" (a private key). Anyone can check the seal using the matching public key, which we publish openly. A child can't write "over 18: yes" and fake the seal.

The letter is deliberately short. It says who it's for (which website), when it expires (minutes, not days), a one-time number so it can't be reused, and "over 18: yes". It never contains the estimated age, a name, or any lasting identifier.

We rejected:

  • returning the answer in the page address (?result=pass), because anyone can type that themselves;
  • notifications without a seal, because anyone can fake them.

Explain like I'm six — a restaurant kitchen

On the outside are the adapters that talk to the web, the database and the AI service. The rules never depend on the outside, so the outside can change without breaking them.

One house with many rooms (the monorepo)

All of Dwarpal lives in one repository, organised like a house:

Room What lives there

Why one repository instead of many?

When one change touches several rooms — say, a new score flowing from the AI room to the dashboard — it lands as one reviewed change. Separate repositories would have to be updated in lock-step, and they eventually drift apart.

The life of a verification session

A session is one visit to the guard. It moves through a fixed set of states:

created → in progress → completed (pass / fail / reject)
                  ↘ awaiting step-up → completed
created or in progress → expired / canceled

These moves are enforced by a tiny program called a state machine. A session can't jump from "created" straight to "completed: pass", and once it is completed it can never change. Tests try every possible move to prove it.

What is stored — and what never is

Kind of data Example Stored?
Biometric camera frames, face crops Never — memory only, for about a second
Identity documents name and passport number from an ID; Aadhaar details Never — only "year and month of birth" survives from a document
Scores "quality 0.92, live 0.98, P(over 18) 0.995" Yes, for 90 days
Metadata session status, which policy, timestamps Yes, for 90 days
Secrets password fingerprints, encrypted signing keys Yes, protected
Audit trail "admin X created API key Y at time Z" Yes, for 1 year, tamper-evident

Even the disk is protected from accidents.

  • The programs that touch faces run on a read-only file system: they physically cannot write files.
  • Their only scratch space is a RAM disk (tmpfs), which vanishes when the program stops.
  • A special test sends a "canary" pattern of bytes through the system and fails if that pattern ever appears in any log.

The decision engine, in order

When the AI room reports back, the guard's rulebook is checked in this order. The first rule that applies wins:

  1. Did anything go wrong? — then retry (never pass).
  2. Were the pictures good enough? — if not, retry, with a helpful hint like "find more light".
  3. Was it really a live person following the instructions? — if clearly not, reject. If unclear, step-up.
  4. Did the frames agree with each other? — if not, retry.
  5. The age line — above the calculated pass line → pass; below the fail line → fail; in between → step-up. Each retry makes the pass line a little stricter.
  6. Too many tries? — then only step-up or fail remain possible.

This rulebook is pure: it never touches the internet, a database or the clock — it just takes inputs and returns an answer. That makes it easy to test thousands of times with random inputs, checking promises such as "a higher chance of being an adult can never turn a pass into a fail" and "missing information can never produce a pass".

Teaching the AI: four jars of photos

Explain like I'm six — homework, practice tests, the ruler and the final exam

Imagine studying for an exam with four piles of questions:

  1. Training jar — the textbook exercises you practise on, again and again.
  2. Validation jar — practice tests that tell you when to stop studying and which study method works best.
  3. Calibration jar — a special test used for one thing only: drawing the guard's line (§3.3, "the jar of photos").
  4. Test jar — the final exam, taken once, at the very end. Nobody peeks at it while studying.

If you studied from the final exam, your score would be meaningless. In AI this mistake is called data leakage, and keeping the four jars strictly apart is how we avoid it. If the same person's photos could land in two jars, the model would partly "remember" them, so we split by person wherever the data says who is who. Duplicate photos are also removed across all jars.

Checking a passport's maths: the 7-3-1 check digit

At the bottom of every passport are two lines of code-like text: the machine-readable zone (MRZ). Here is the second line of the official specimen passport published by ICAO (the UN agency that standardises passports). It belongs to the fictional Anna Maria Eriksson of the fictional country Utopia:

L898902C36UTO7408122F1204159ZE184226B<<<<<10

Hidden in it is the date of birth 740812 (12 August 1974), followed by a check digit, 2. A check digit is a tiny piece of arithmetic that catches misreadings. Multiply the digits by the repeating weights 7, 3, 1, add everything up, and keep the last digit:

Character 7 4 0 8 1 2
Weight 7 3 1 7 3 1
Product 49 12 0 56 3 2

49 + 12 + 0 + 56 + 3 + 2 = 122, and the last digit of 122 is 2 — the check digit printed in the passport. If the camera misread a single digit, the sum would almost certainly come out different, and we would know.

Letters count too: A = 10, B = 11, … Z = 35, and the filler character < = 0. Our MRZ reader checks every check digit before believing a single date.

Honest limitation

Check digits catch mistakes, not forgeries: anyone can calculate a correct check digit for a fake date. Real passports also contain a chip with a digital signature, but web browsers can't read it. That's why Dwarpal labels the MRZ check honestly as basic assurance.

The Aadhaar Secure QR: a government wax seal

The Secure QR code printed on Aadhaar documents contains the holder's details and photo, digitally signed by UIDAI — the same "wax seal" idea as our own tokens (§3.3, Choice 9). Dwarpal can check that seal using UIDAI's published public key, read only the date of birth, compare the QR's photo with a live selfie, and then forget everything. Because Aadhaar data is legally sensitive, the feature is off by default outside India, asks for explicit consent, stores nothing, and is marked as needing legal review before real-world use.

Key idea — the clean room

The inference service is a clean room: faces go in, numbers come out. It sits on a private network with no way out to the internet and a disk it cannot write to. Even if someone slipped bad code inside, it would have nowhere to send stolen faces and nowhere to store them.

Trust zones. We sort every place in the system into zones by how much we trust it:

  • the user's device is untrusted — everything it says is re-checked;

On the internet: one rented Linux server runs all the containers with Docker Compose. Caddy faces the internet, and each zone has its own private network. Backups are encrypted every night and stored somewhere else. A Kubernetes version of the same layout is kept ready in case the system ever needs to grow beyond one server.

4.1 Git in practice

§0.15 introduced Git as a time machine for code. Here is what actually happens inside the project folder.

  • git init -b main turned the folder into a repository (Git keeps its own data in a hidden .git folder). -b main names the first branch main.
  • The files you edit form the working tree.
  • git add puts chosen changes into the staging area — a draft of the next snapshot.
  • git commit saves the staged draft as a permanent commit: a snapshot of every tracked file, plus a message, the author, the time, and a pointer to the previous commit. Commits form a chain, which is the project's history.
  • A remote (like GitHub) is another copy of the repository that you push commits to and pull commits from.

Where we are

The repository has been initialised, but nothing has been committed yet. Committing is the project owner's call, and it is offered at the end of Phase 0.

Files Git must never see: .gitignore

Some files must never enter history:

  • secrets (.env files with passwords) — once committed, a secret is in history forever, even if deleted later;
  • downloaded or generated bulk (node_modules, .venv, caches) — huge, and rebuildable from the lockfiles;
  • datasets and model weights — huge, and licence-restricted (§0.16).

.gitignore lists patterns of paths Git should pretend don't exist. Its walkthrough is in §5.0.1.

Line endings: .gitattributes

Windows ends each line of text with two invisible characters, carriage return + line feed (CRLF). Linux and macOS use only line feed (LF). If a Windows editor and a Linux server disagree, every line of a file appears "changed" for no visible reason, and shell scripts can break.

.gitattributes tells Git to store every text file with LF, whatever computer it was edited on. It also marks images and model files as binary, so Git never tries to "fix" their bytes.

4.2 How Python projects are organised

Modules, packages and distributions

Word Meaning Example
Module One .py file build.py
Package A folder of modules, marked by an __init__.py file dwarpal_api/
Distribution A package bundled for installation, with a name and version dwarpal-api 0.1.0

The distribution's name uses a dash (dwarpal-api). The importable package uses an underscore (dwarpal_api), because a dash isn't allowed in a Python name — Python would read it as a minus sign.

The src layout

Each of our packages keeps its code in a src/ folder: services/api/src/dwarpal_api/__init__.py.

Why the extra src folder?

Without it, Python can accidentally import your package straight from the folder you're standing in, even if it isn't installed properly. Tests would then pass on your machine and fail on a server. The src layout forces the code to be installed before it can be imported, so you always test what you ship.

pyproject.toml

Every modern Python project describes itself in a pyproject.toml file (TOML, see Part X). The official sections are:

  • [project] — name, version, description, supported Python versions, dependencies;
  • [build-system] — which build backend turns the folder into an installable distribution. We use uv_build, the fast backend made by the uv team;
  • [tool.*] — settings for tools (ruff, mypy, pytest, uv).

Virtual environments

Different projects need different library versions. A virtual environment (.venv) is a private folder holding one Python interpreter plus exactly the libraries one project needs. Projects can't interfere with each other, and the computer's own Python stays clean.

uv — one tool for all of it

uv is a very fast Python project manager written in Rust. In this project it:

  1. installs Python itself. This computer's own Python is 3.14, but the project pins 3.13 (in .python-version), so uv downloaded its own copy of Python 3.13.16;
  2. creates the virtual environment (.venv at the project root);
  3. resolves dependencies — it works out a set of library versions that fit together — and writes them to the lockfile uv.lock;
  4. installs exactly the locked versions (uv sync);
  5. runs commands inside the environment (uv run …), syncing first if anything changed.

Workspaces. Our five Python packages (api, inference, contracts, vision, ml) are members of one uv workspace: one lockfile and one environment for all of them, installed in editable mode so code changes take effect immediately. Every package therefore always sees the same version of every library.

Dependency groups. Tools only developers need (ruff, mypy, pytest) live in a dev group; the book's tools (Markdown, Pygments) in a docs group. They are never shipped inside a service.

Alternatives considered

  • pip + venv — built in, but has no lockfile and no Python installation, and is slow on big projects.
  • Poetry — popular, but slower, with its own non-standard metadata and no Python installation.
  • conda — great for scientific stacks, but heavy, and mixes non-Python packages into the environment.

uv does all of it, follows the official standards, and is 10–100× faster than pip.

Real world — what we measured

uv sync resolved and installed the workspace's 21 packages in under 3 seconds on first run (most of it downloading). Re-runs take milliseconds.

4.3 Four robots that check every change

People make mistakes; robots don't get tired. Every change in this project passes four automatic checks.

Robot 1 — the formatter (ruff format)

A formatter rewrites code into one consistent layout: spacing, line breaks, quotes. Nobody argues about style, and code reviews focus on meaning. It changes files; in CI it runs with --check, which only reports.

Robot 2 — the linter (ruff check)

A linter reads code without running it and flags likely bugs, risky patterns and outdated style. Ruff is a Rust-based linter that implements over 800 rules from many older tools, in milliseconds. We switched on these rule families:

Code Family Catches, for example
E, W pycodestyle Lines too long, stray whitespace
F Pyflakes Unused imports, undefined names — often real bugs
I isort Imports in a messy order
B bugbear Classic traps, such as a mutable default argument shared between calls
UP pyupgrade Old syntax with a modern replacement
SIM simplify Needlessly complicated if/else
C4 comprehensions Loops that should be comprehensions, and the reverse
PTH pathlib os.path string juggling instead of Path objects
S bandit (security) subprocess with a shell, weak hashes, hard-coded passwords
N naming camelCase where Python expects snake_case
RUF Ruff's own Ambiguous Unicode characters, and more
DTZ datetime Times without a time zone — a classic source of bugs
PERF performance Slow patterns in loops
RET return Inconsistent return statements

Real world — the first thing Ruff caught

On its very first run, Ruff flagged one line in the book builder: datetime.now(timezone.utc) should use the newer, clearer alias datetime.now(UTC). Small, but it shows the robot reading every line.

Robot 3 — the type checker (mypy --strict)

Python doesn't make you declare what kind of value a variable holds. The type hints we write (def read_text(path: Path) -> str) are labels for humans and tools. mypy reads those labels and proves that the code uses them consistently: you never pass a number where text is expected, never forget that something might be None, and so on. --strict turns on every check, including "every function must be fully labelled".

Real world — what strict mode changed in this phase

mypy refused two things in the book builder:

  1. A bare dict must say what it contains, so it became dict[str, Any]: keys are text, values can be anything.
  2. The Markdown library attaches a toc_tokens attribute to its converter while the program runs, so a type checker reading the code beforehand can't know it exists. The fix, getattr(md, "toc_tokens", []), reads the attribute safely and also says what to use if it's missing.

Neither was a bug yet, but both were places where a future change could have caused one without warning.

Robot 4 — the tests (pytest)

A test is a small program that runs a piece of real code with known inputs and checks the result:

def test_fingerprint_is_stable_and_changes_with_any_edit() -> None:
    assert build.fingerprint("x = 1\n") == build.fingerprint("x = 1\n")
    assert build.fingerprint("x = 1\n") != build.fingerprint("x = 2\n")

assert means "this must be true — otherwise stop and report a failure". pytest finds every function whose name starts with test_, runs them all, and reports which passed. Phase 0 has 9 tests, all for the book builder, because the program that checks the book must itself be checked.

4.4 The JavaScript side

Node.js

Node.js runs JavaScript outside the browser — on servers and on developers' machines. It is what will run our Next.js websites, and all the JavaScript tools. Versions with even numbers become LTS (Long-Term Support) releases, maintained for about three years. We use Node 24 LTS.

npm, pnpm and the lockfile

npm is Node's built-in package manager. We use pnpm instead:

  • it stores each version of each library once on the computer and links it into projects, saving gigabytes;
  • it is stricter — a package can only use libraries it actually declares, which prevents "works on my machine" bugs;
  • it has first-class workspaces.

package.json records the exact pnpm version in its packageManager field, so every machine uses the same one. pnpm install writes pnpm-lock.yaml, the JavaScript lockfile.

Careful — install scripts are a security risk

When we installed pnpm itself, npm printed: "1 package has install scripts not yet covered by allowScripts". An install script is code that a package runs automatically on your computer at install time — a favourite trick of malicious packages. Modern npm and pnpm therefore block them unless you approve them. Every install script in this project must be approved deliberately.

Workspaces and Turborepo

pnpm-workspace.yaml says which folders hold workspace packages (apps/*, packages/*). The first package is @dwarpal/config, which holds the shared TypeScript settings.

Turborepo (turbo) runs tasks — build, typecheck, test — across all packages in the right order, and caches the results. If a package hasn't changed, its previous result is reused instantly. In turbo.json, "dependsOn": ["^build"] means "before doing this task for a package, build every package it depends on". The ^ means dependencies, not the package itself.

Where we are

Turbo currently prints "No tasks were executed": no package has a build or test script yet. The apps arrive in Phase 1.

Biome

Biome is the JavaScript world's version of Ruff: one fast tool (written in Rust) that formats and lints JavaScript, TypeScript, JSON and CSS. It replaces the older pair of ESLint and Prettier.

Real world — keeping up with tools

Biome 2.5 printed a warning on our first configuration: the "recommended": true setting is deprecated in favour of "preset": "recommended". Running biome migrate --write rewrote the configuration automatically. Tools change; reading their warnings, not ignoring them, keeps a project healthy.

TypeScript settings

packages/config/tsconfig.base.json holds the strictest sensible TypeScript settings. Every app and package will extend it, so all of them follow the same rules. Each option is explained line by line in §5.0.4.

A decision deliberately postponed

TypeScript 7 (a complete rewrite of the compiler in the Go language) became the default version on npm in 2026. Whether Next.js 16.4 and the other tools work smoothly with it will be tested in Phase 1, when the first TypeScript code exists. Until then nothing depends on it, so nothing is pinned.

4.5 Docker Compose in practice

§0.14 explained images, containers and volumes. Here is what our first Compose file actually does (full walkthrough in §5.0.5):

  • Pinned image tags. postgres:18.6-alpine3.24 means PostgreSQL version 18.6, built on Alpine Linux 3.24 — a tiny Linux distribution, so images are small. A bare postgres:latest would silently change under us.
  • Settings with defaults. ${POSTGRES_PASSWORD:-dwarpal-local-only} means "use the environment variable if set, otherwise this default". The defaults are deliberately labelled local-only.
  • Ports bound to 127.0.0.1. 127.0.0.1:5432:5432 makes the database reachable only from this computer, not from other devices on the same Wi-Fi.
  • Health checks. Docker asks each container "are you ready?" every 5 seconds (pg_isready, valkey-cli ping). docker compose up --wait waits until every container reports healthy, not just "started".
  • Volumes. The data lives in named volumes (pgdata, valkeydata), so it survives restarts.

4.6 Continuous integration with GitHub Actions

Continuous integration (CI) means: every time anyone pushes code, a robot in the cloud checks out a fresh copy and runs every check. Because it starts on a clean machine each time, "it works on my computer" stops being an excuse.

On GitHub, CI is described in workflow files under .github/workflows/, written in YAML (a settings format based on indentation). Their building blocks are:

Word Meaning
on Which events start the workflow (a push to main, a pull request)
jobs Independent groups of work. They run in parallel on separate fresh machines
runs-on The kind of machine, e.g. ubuntu-24.04 (a Linux virtual machine)
steps The commands of a job, in order. uses: runs a published action (a reusable step); run: runs a shell command
permissions What the workflow may do on GitHub. We grant only contents: read — the principle of least privilege

Our workflow has three jobs:

  • Python — uv run tasks.py check;
  • JavaScript — lint, typecheck, test;
  • Compose — the databases must start healthy.

Where we are

The workflow file is written and valid, but it has never run, because the project isn't on GitHub yet. It runs automatically the first time the repository is pushed.

4.7 One command to check everything: tasks.py

Every check has its own command — ruff, mypy, pytest, the book builder. Remembering them all is error-prone, so tasks.py gives them short names:

uv run tasks.py check

That one command runs everything CI runs, stopping at the first failure, and prints which step failed.

Why a Python script instead of a Makefile?

make is the classic tool for this, but it isn't installed on Windows by default and behaves differently across systems. A tiny Python script needs nothing but the Python the project already has, and works the same on every operating system.

X.1 Why a program builds this book

The book you are reading is a single HTML file. We could have typed that HTML by hand, but three problems would appear quickly:

  1. It would be huge and painful to edit. Thousands of lines of HTML tags around every sentence.
  2. It would drift away from the code. When a code file changes, nothing would tell us that its explanation is now wrong.
  3. "Every line is explained" would be a promise nobody could check.

So the book is generated. We write chapters in a simple text format (Markdown) and explanations in small walkthrough files. A Python program, build.py, then assembles them into the HTML file. While doing so it checks the coverage and freshness of every explanation.

Explain like I'm six

Instead of hand-copying a whole book every time one page changes, you keep each page separately and let a machine bind them into a book. The machine also checks each page against the thing it describes and puts a red sticker on any page that's out of date.

X.4 How a walkthrough file works

A walkthrough file has three parts.

1. A header between two lines of three dashes, recording the code file's fingerprint at the moment it was explained:

---
fingerprint: 3f9a1c0be27d4e51
---

2. An introduction — ordinary Markdown describing the whole file.

3. Notes. Each note starts with a line containing two @ signs and a line number (like @@ 12) or a range (like @@ 12-14). The explanation of those lines follows in Markdown:

@@ 1
This line ...

@@ 2-4
These three lines ...

Inside a chapter, a line that contains only the word !walk followed by a file path tells the builder: "put the line-by-line walkthrough of this file here". A line containing only !ledger inserts the coverage table.

X.5 Fingerprints

How can a program notice that a file changed since it was explained? It can't keep a copy of every old version. Instead it keeps a fingerprint.

Explain like I'm six — the magic blender

Imagine a magic blender. You drop in any amount of text — one word or a whole book — and it always pours out a short code like 3f9a1c0be27d4e51. Two magic rules:

  • the same text always gives the same code;
  • change even one letter, and the code comes out completely different.

So to know whether a file changed, you don't need the old file — only the old code.

The blender is a real algorithm called SHA-256, a cryptographic hash function used everywhere in computer security, including in Git and HTTPS certificates. SHA-256 produces 64 hexadecimal characters (digits 0–9 and letters a–f). We keep the first 16. That is still 2⁶⁴ ≈ 18 quintillion possibilities — far more than enough to notice an edit.

X.6 Coverage and the ledger

For each code file the builder:

  1. counts the non-blank lines (blank lines have nothing to explain);
  2. marks the lines covered by a note that has real text — a note that is empty, or still says TODO, does not count;
  3. shows any uncovered line in the book with a red bar and the words "Not explained yet";
  4. compares the recorded fingerprint with a fresh one, and shows a red "code changed since explained" badge if they differ.

Then it walks the whole project folder, finds every code file, and prints the Coverage ledger. Files with no walkthrough at all appear there as not explained. Nothing can hide.

When code changes: re-anchoring

Notes are pinned to line numbers. Add one line at the top of a file and every note below it now points one line too high. In the first days of this book, fixing that meant renumbering notes by hand — slow and error-prone.

So the builder learned a trick. Whenever a walkthrough is stamped, the builder also saves a snapshot: a copy of the source file exactly as it was explained. Later, --reanchor compares the snapshot with the current file and works out where every unchanged line has moved:

  • a note whose lines are all unchanged simply moves with them — no human needed;
  • a note whose lines were edited moves to the new code that replaced them, and its text is prefixed with TODO(review). It then counts as not explained until someone re-reads it and removes the prefix;
  • a note whose lines were deleted is dropped, and the command prints what was dropped.

Explain like I'm six — seats in a theatre

Imagine a theatre where every seat has a name card. The theatre adds two new rows at the front. Every old seat now has a new number, but the people haven't changed — so you move each name card to its person's new seat number. If someone swapped seats with a stranger, you put a sticky note on their card: "please check this one".

How does the builder know which lines are "the same"? Python's built-in difflib module finds the longest runs of lines that appear in both versions, in the same order — the same idea behind the "diff" view of any code-review tool.

Key idea

Moving notes is automatic. Approving them is not: only a person can confirm that an explanation still matches the code. That is why --reanchor never stamps, and why changed notes are marked TODO(review).

book.toml holds the book's settings. Keeping settings in a separate file, rather than inside build.py, means you can add a chapter or change the title without touching any program code. "Separate the what from the how" is one of the oldest good habits in software.

The file is written in TOML ("Tom's Obvious, Minimal Language"):

  • name = value sets a value;
  • text goes in double quotes;
  • lists go in square brackets;
  • a line like [coverage] starts a named group of settings, which TOML calls a table.

Python reads TOML with its built-in tomllib.

Alternatives considered

  • JSON doesn't allow comments and is fussy about commas.
  • YAML has surprising rules: the unquoted word no can turn into false.

TOML is what Python's own packaging uses (pyproject.toml), so it is the natural choice for a Python tool.

X.9.3 template.html — the page shell

docs/zero_to_hero/template.html200 lines · 100% explained

template.html is the empty shell of the book's page. It contains everything except the content: the page structure (HTML), all the styling (CSS, inside <style>) and the small amount of behaviour (JavaScript, inside <script>). Where content belongs it has blanks written as a word in double curly braces — {{TITLE}}, {{TOC}}, {{BODY}} and so on. build.py fills them in (see its lines 255–264).

The book must work as one file, offline, with nothing downloaded from the internet, so everything is inline: no external stylesheets, scripts or fonts.

CSS in one minute. A CSS rule looks like selector { property: value; property: value; }:

  • the selector says which elements the rule applies to — h1 means every <h1>, .side every element with class="side", #q the element with id="q";
  • each property: value pair says how they should look.

When several rules apply to the same element, the more specific selector wins. Between equally specific rules, the one written later wins.

JavaScript in one minute. JavaScript is the browser's programming language. Here it does four small jobs:

  1. remember and switch the colour theme;
  2. filter the sidebar;
  3. highlight the section you're reading;
  4. draw the reading-progress bar.
1<!doctype html>

<!doctype html> — the first line of every modern web page. It tells the browser "this is modern HTML; use standard rules". Without it, browsers fall back to an old compatibility mode ("quirks mode") that lays pages out differently.

2<html lang="en">

<html lang="en"> — the start of the page. Everything else sits inside it. lang="en" declares the language as English, which helps screen readers pronounce words correctly and helps browsers offer translation.

3<head>

<head> — the page's "behind the scenes" section: settings, title and styles. Nothing in the head is shown directly in the page.

Glossary

Every technical word used in the book, in alphabetical order. The section in brackets is where the idea is first explained.

Age assurance
Any method of establishing someone's age with some level of confidence. The umbrella term for verification, estimation and inference. (§1.5)
Age estimation
Guessing age from a physical characteristic, usually the face. Fast and private, but it always carries some error. (§1.5)
Age inference
Deducing age from other facts, such as holding a credit card. (§1.5)
Age verification
Establishing age from an authoritative source, such as an ID document or a digital-ID app. (§1.5)
API
Application Programming Interface. A menu of requests one program offers to other programs. Each request it accepts is an endpoint. (§0.11)
Argument
A value handed to a function or a command. In python build.py --strict, --strict is an argument. (Part X)
Audit log
A permanent, ordered record of important events (who changed what, when). Ours is tamper-evident: each entry includes a fingerprint of the previous one. (§3.3)
Backend
The programs that run on servers, out of the user's sight. (§0.10)
Biometric data
Information about a person's body, such as their face. (§1.11)
Bit, byte
A bit is a single 0 or 1. A byte is 8 bits, enough for a number from 0 to 255. (§0.1)
Buffer / challenge age
An extra margin above the legal age. For example, "pass only if the estimate is 25 or more, for a legal age of 18". (§1.8)
Certificate
A digital document, signed by a trusted organisation, proving a server's identity for HTTPS. (§0.9)
Client
A program that asks a server for something — for example, a web browser. (§0.7)
Clopper–Pearson bound
A method for working out, from a test result like "6 out of 600", the worst plausible true rate at a chosen confidence level. (§3.3)
Code / source code
The human-readable instructions of a program, written in a programming language. (§0.3)
Commit
A saved snapshot of a project in Git, with a message explaining the change. (§0.15)
Compiler
A program that translates a whole program into machine code before it runs. (§0.4)
Container
A running copy of a Docker image. (§0.14)
Coverage
In this book: the share of a file's non-blank lines that have an explanation. (Part X)
Database
A program that stores data permanently and answers questions about it quickly and safely. (§0.12)
Dataclass
A Python shortcut for defining a class that mainly holds data. (Part X)
Deploy
To copy a program onto a server and start it there. (§0.13)
Dictionary (dict)
A Python collection of labelled values, looked up by key: {"title": "Dwarpal"}. (Part X)
DNS
Domain Name System. The internet's phone book, turning names into IP addresses. (§0.6)
Docker / image / volume
Docker packs a program with everything it needs into an image. A volume is a folder that survives when containers are thrown away. (§0.14)
Domain
A human-friendly internet name, such as dwarpal.example. (§0.13)
Encoding
The agreement that maps characters to numbers. We always use UTF-8. (§0.2)
Endpoint
One specific request an API accepts, identified by a method and a path, such as POST /v1/verification-sessions. (§0.11)
Extension (file)
The letters after the last dot in a file name, such as .py, hinting at the kind of file. (§0.2)
Fail closed
When something goes wrong, the system chooses the safe answer ("retry" or "step-up"), never "pass". (§1.13)
False-adult rate
The share of children near the age limit whom the system wrongly lets through. Our most important safety number. (§1.7)
Fingerprint (hash)
A short code computed from a file's contents. Change one character and the fingerprint changes completely. (Part X)
Frontend
Everything that runs in the user's browser. (§0.10)

A named, reusable block of code that takes inputs and gives back a result. (Part X)
Git, GitHub
Git records a project's history as commits. GitHub stores Git projects online. (§0.15)

Graphics Processing Unit. A chip that performs thousands of calculations at once — ideal for AI. (§0.1)

Renting computers in a data centre to run your website. (§0.13)

The skeleton, the clothes and the muscles of a web page. (§0.10)

The protocol browsers and servers use to talk. HTTPS is HTTP inside TLS encryption. (§0.8, §0.9)

A program that runs code by reading it line by line. (§0.4)
